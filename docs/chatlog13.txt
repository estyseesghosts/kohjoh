● The two lit lists are probably the most expensive draws left in Goldenrod that
  the display-list cache can't replay. That they stay on the slow path because
  of matrix commands inside them is a suspicion I haven't confirmed yet.

  What they are
  - Each is a ~1,050-word display list: 32-bit commands and parameters that the
    game sends to the DS geometry engine in one call. At that size it is a few
    hundred vertices with normals.
  - The profiler only knows the address of the code that sends them (0x5846f4).
    I haven't yet identified which model they are.

  How a list normally gets cheap
  On first sight, kj_g3.c decodes a list while recording it. If the recording
  comes out clean, the list is cached. Lit lists whose lighting doesn't change
  are lit once on the CPU and from then on replayed as plain coloured geometry.
  That is the main saving from this session.

  Why these two don't
  The recording is marked bad, so the list falls back to the live path
  (kj_g3.c:3805-3813): it is decoded word by word on every call, each vertex
  goes through the per-vertex path, and the GPU lights it with the lit shader.
  That costs about 128K Azahar ticks per call.

  A recording can be marked bad for these reasons:
  1. Dropped or unsupported geometry (:3780).
  2. Blocks sharing vertices with an earlier block (:2192).
  3. Command 0x50 inside the list (:2248).
  4. The list's colours depend on its normals and it also contains matrix 
     commands (0x10-0x1C) (:3787). This is the one I suspect.

  Why reason 4 blocks caching: a lit vertex's colour depends on its normal times
  the current direction matrix. A list that restores or loads matrices partway
  through (one matrix per bone or part, for example) lights its later vertices
  with matrices that weren't in place when the list was called. The cache key
  only describes the state at the start of the list. A baked copy could
  therefore show stale lighting whenever those stored matrices change, so the
  code refuses to bake.

  What it costs
  Two lists at about 128K ticks each come to roughly 1 ms per picture in Azahar.
  The worklog's ~2 ms per picture is the O3DS estimate, since hardware runs
  about 2.3× slower than Azahar. That is about 6% of the 33.4 ms budget. The GPU
  also lights every one of those vertices, which Azahar doesn't time.

  The planned fix, if reason 4 is confirmed
  Add the rotation part (3×3) of the matrices the list restores to the cache
  key. If those matrices don't change from frame to frame, the key matches and
  the list bakes like the static scenery. If they do change every frame (an
  animated model), it correctly stays on the live path, and the remaining option
  is to make that path cheaper.

  build/opt-tools/diag_gpulit.py adds a temporary log that prints which reason
  fired, the list's command mix, and whether the matrices it uses change between
  calls. One Azahar run of that build will settle it.
