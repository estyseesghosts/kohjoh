● kohjoh: where things stand

  The rebuild finished and the four Ho-Oh render experiments are running in
  Azahar now.

  What it is

  kohjoh is a new HeartGold/SoulSilver port to the 3DS. It compiles the
  decompiled game code (about 1,100 C files from pokeheartgold) against a
  compatibility layer that stands in for the Nintendo DS system libraries.
  Underneath is a 3DS runtime that redraws the DS display on the 3DS GPU:
  - 2D: tiles and sprites go through a texture atlas, so all layer drawing runs
    on the GPU.
  - 3D: the CPU reads the DS 3D command stream, and the 3DS GPU transforms the
    vertices.

  The DS game code and the 3DS code only connect through kj_bridge.h. This is a
  fresh start after the older hgss-3ds port. There are 9 commits so far, and
  only HeartGold is built.

  What works (seen running in the Azahar emulator)

  - Boot, the intro movie, the title screen, menus, and continuing a save into
    the Goldenrod overworld.
  - 2D graphics: layers, sprites, priorities, blending, windows, and effects
    that change per line. Intro frame 1650 matches our offline DS reference
    renderer.
  - 3D: textures, lighting and the widescreen field on the top screen, all
    checked on New Bark and Goldenrod.
  - Buttons and touch input.
  - Save loading (the previous agent's fix). It still uses an interim raw .sav
    file.
  - Audio: you heard music on your end. My Azahar has no DSP firmware, so I
    can't hear it here.
  - Today: the title screen's lower screen now shows Ho-Oh instead of black. The
    cause was that the DS uses W-buffer depth mode for that scene, which the
    port didn't handle. Commit 4661af7.

  What's broken or unproven

  - Ho-Oh's wings have chunks missing. I'm testing which render state causes it
    (culling, depth, alpha test or blending) against melonDS screenshots. I
    won't touch the vertices, so no stretching.
  - Battle crashes: not reproduced yet. A crash handler is installed that writes
    logs/crash.txt, and a scripted run to a Route 34 wild battle is written but
    not run yet.
  - Intro stutter: measured. The worst hitches are in the 2D path:
    - game frames 872–883: 17–34 ms spikes, plus one 74 ms logic spike;
    - frames 987 and 1095;
    - an 89 ms spike while the title screen loads.

    New per-hitch counters, built into this run, should say whether tile
    conversion, texture uploads or something else causes them.
  - Performance on real hardware is unknown. Nothing has been measured on an Old
    3DS. Azahar only gives instruction counts, which are a lower bound.
    Goldenrod costs about 25 ms of game logic per frame, mostly 3D geometry
    decoding, which is tight against a 33 ms budget. Locked 30 FPS on an Old 3DS
    is not established and is doubtful at these numbers.
  - Display-list cache (a speed feature): off on master, because enabling it
    corrupts memory.
  - The wip/savestore branch doesn't build. It holds:
    - the proper save system;
    - the fixed display-list cache;
    - a regression where the bench save is no longer detected.
  - Not built yet: CIA packaging, packing game data into the app (RomFS), the
    3DS save archive, and the SoulSilver build.

  How complete

  About 60–70% of the way to playable, and well short of shippable. The full
  game runs from boot to the overworld, and both 2D and 3D rendering are largely
  right. What's missing:
  - the battle crashes are unfixed;
  - 3D still has visual bugs, like the Ho-Oh wings;
  - smooth 30 FPS is unproven;
  - the final save format, packaging and SoulSilver are not done.

  The biggest risk is Old 3DS performance, not correctness.

● Ho-Oh's missing wing chunks are fixed. Both wings are now whole, and title
  frames 2300 and 2500 match melonDS in Azahar. The vertices are untouched; the
  fix is in the matrices.

  fixed (build/azahar/g3fix/f02300.png)

  Root cause: the port treats the DS 3D-command registers as ordinary memory.
  When code writes one directly (for example reg_G3_MTX_STORE = …) instead of
  going through the port's command path, the write is silently lost. The library
  code that blends Ho-Oh's wing bones does exactly that, so the blended
  matrices were never stored. Each wing vertex then picked up an all-zero matrix
  and collapsed onto a single point, which left those triangles with no area:
  41 zero matrices per frame. The old port's "stretched" Ho-Oh was a workaround
  drawing those collapsed triangles anyway.

  How I found it:
  - Four experiments turning off culling, depth test, alpha test and blending
    changed nothing, so the GPU stage wasn't to blame.
  - I then wrote each frame's decoded 3D scene to a file and drew it with a
    separate offline tool (tools/capture/g3_reference.py). It showed the same
    holes, so the geometry itself was wrong.
  - A trace pointed at matrix-stack restores from slots that had never been
    written.

  Fix: three new patches send these writes to the port's geometry engine. The
  original DS code is kept in #else branches.
  - NitroSystem 0305: the bone-blending code, plus two other spots that read
    matrices back.
  - NitroSDK 0606: the 3D init/reset code, which was not resetting the matrix
    stacks between scenes.
  - pokeheartgold 2004: game files with the same problem: the Pokémon summary
    screen, Safari decorations, Pokéathlon, dress-up, the Apricorn box and the
    Wi-Fi plaza. I fixed these by a scan of the source tree but have not run
    those scenes.

● I rewrote docs/building-windows.md (commit 92a9a6d) and tested it by following
  it exactly from scratch, with empty build/upstream and build/kj. All 91
  patches applied, the build finished with 0 errors in about 6 minutes, and the
  title screen with the fixed Ho-Oh checked out in Azahar.

  Two problems the fresh build turned up, both now in the doc:
  - Bootstrap fails over HTTPS. devkitPro's MSYS2 git can't fetch over HTTPS
    (git-remote-https.exe: error while loading shared libraries). The fix is to
    put Git for Windows first on PATH inside the build shell.
  - The build can report success while using stale libraries. If the SDK or
    NitroSystem code fails to compile, the build quietly links the old prebuilt
    libraries and still produces a .3dsx. The doc now says to treat a build as
    good only when the log ends in packaged and contains no error: or vendored 
    library build failed lines.

  What the doc now covers:
  - Where to run it: inside devkitPro's MSYS2 login shell (bash.exe -lc), which
    sets DEVKITPRO and DEVKITARM.
  - Required flags: --target 3ds must be passed, because the default is a PC
    test build. Absolute /c/... paths are required.
  - Every hgss_game.py argument.
  - Every --define switch:
    - KJ_G3_PROFILE and KJ_G3_ZERO_TRACE are diagnostics.
    - KJ_DL_CACHE is marked unsafe on master.
  - Legacy HGSS_* variables from hgss-3ds: what each still does in kohjoh. Only
    HGSS_PROFILE=off, HGSS_SND_ADPCM and HGSS_A0_DIAG change anything. The
    HGSS_GX3D_*, HGSS_TEXTURE_* and HGSS_PALETTE_HASH ones have no effect.
  - When inline environment variables work: they reach the build inside the -lc
    shell, but are dropped when MSYS2 Python is started directly from Git Bash.
    --define works either way.
  - Outputs and timings: what the build produces (.3dsx, .elf for crash
    addresses, build-info.txt), how long it takes, and how incremental rebuilds
    work.
  - Changing the decomp, NitroSDK or NitroSystem: edit and commit in
    build/upstream, export with git format-patch into the matching patches/
    folder, and run bootstrap.py --clean after switching branches.
    check_patches.py catches a missing patch but not an extra one from another
    branch, which is how the stray patch 2003 got into my earlier builds.

  build/upstream.pre-clean and build/kj.pre-clean; nothing in them is unsaved,
